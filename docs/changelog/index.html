What's new

Every Orca release, newest first. Orca updates itself, so you get these as they ship.

v0.50.1October 22, 2026

#Run Orca from Claude: one click, no tokens

Orca is an MCP server, and connecting your AI tool to it now takes one click. Open Settings → AI & Agents and press Connect next to Claude Code, Claude Desktop, Cursor, VS Code, Windsurf or Codex. Orca shows which of them are on your computer and adds itself to their config, leaving everything else in the file alone.

Then just ask: "Start the project in ~/code/shop and give me its URL", "Turn on the search profile", "Why does the api container keep restarting?"

  • No tokens to copy. The AI tool runs orca mcp, which reads Orca's token itself. Nothing secret ends up in an AI tool's config or a committed .mcp.json.
  • Uses the subscription you already have. No API key or per-token billing: Claude Pro/Max, ChatGPT, Cursor and Copilot plans all work.
  • Survives updates. Orca keeps its own copy of the CLI and refreshes it on start, so updating or moving the app doesn't break anything.
  • From a terminal too: orca mcp install connects every AI tool it finds, and orca mcp status shows where things stand.
  • Remote hosts: orca mcp --host build-server lets an AI tool manage a host from Remote Hosts.
  • If one of your AI tools is installed but not connected, the dashboard invites you to connect it.

#Your AI can now do (almost) everything you can

21 new tools, 69 in total, so an AI tool can manage projects from start to finish:

  • Projects: deploy_project starts a folder with a compose file or orca.yaml; add_project / list_projects / remove_project handle worktree projects.
  • Stacks: restart, pull, logs, switching compose profiles, and reading and writing orca.yaml (validated before it's saved).
  • Gateway: status, start, stop, and listing, adding and removing routes.
  • Builds: list targets, start a build, follow its status and log.
  • Volumes: remove one.

They run through Orca's own API, so they validate exactly as the app does. Tools that delete or overwrite something are marked so your AI tool asks you first.

#The built-in assistant goes local

The chat window behind ✦ is now optional and built for models on your own computer: free, private, and offline.

  • Finds your model servers. Orca looks for Ollama, LM Studio and llama.cpp's llama-server, and lists their models. Pick one and click Use. No key needed.
  • Made for small models. A local model gets a lean set of 19 tools and up to five minutes per answer.
  • Ollama in a container on Linux and Windows now pulls qwen3:8b. On a Mac, Orca suggests the Ollama or LM Studio app instead, since containers there can't use the GPU.
  • Cloud API keys (Anthropic, OpenAI, Gemini, any OpenAI-compatible endpoint) are still there under Cloud API key, with current Claude models.
  • When no model is set up, the assistant window offers to connect Claude instead, and Ask AI on a container or build gives you the question to paste.

#Fixes

Writing the new docs at orca-desktop.com turned up a list of things that didn't work as described. They do now:

  • Schedules run in your local time, not UTC.
  • Stacks with several compose files start with all of them, and the stack page lets you pick which files are used.
  • Kubernetes: enabling Orca's cluster no longer changes your kubeconfig's current context. Port-forwarding services works, jobs show their logs, deployments and services show their labels and selectors, and start, stop and reset work on macOS (Lima).
  • Auto-deploy webhooks: Docker Hub webhooks can authenticate with ?token=, tag rules are enforced, and pulls use your saved registry credentials.
  • Cleanup only ever deletes Orca's own Lima VM.
  • orca deploy accepts a project folder or a compose file inside one.
  • Saving gateway settings restarts the gateway so the change takes effect, and the landing page merges sections with the same name.
  • dev.start: on-create starts new worktrees as it should.
  • The assistant blanks out secrets (passwords, tokens, DATABASE_URL and the like) in tool results before they reach the model.
  • On macOS, Start Docker restarts the VM when the engine is down.
  • Settings only offers GPU options when there's a GPU, and shows where an AI key comes from (setting or environment variable).

v0.50.0October 22, 2026

#Run only the parts of a project you need

Not everyone needs search, mail catchers and admin tools running all day. Orca now uses Docker Compose's own profiles for this, so there's nothing Orca-specific to write down: give optional services a profile in your compose file, and switch them on and off in Orca.

services:
  search:
    image: elasticsearch:8
    profiles: [search]
  • Profiles as cards. A stack's page shows its profiles above its services, with the services in each and which of them run. Switch them and Orca shows what will start and what will be stopped before you press Apply.
  • Your choice sticks. Orca remembers the set for each stack on your machine and starts the same set every time, from the stack page, orca deploy or an AI agent. Teammates each pick their own, and nothing is committed.
  • No surprises. If a service you switch on needs one whose profile is off, Orca says so and offers to switch it on. Services that are off are still listed, with a button to bring them back. Setup commands for services that don't run are skipped instead of failing.
  • Worktrees too. The Start dialog has the same cards, and each worktree remembers its own choice: orca up --profile search.

Presets (dev.instance.presets) are retired in favour of profiles. Orca ignores them in existing files and the editor tells you so. See Running only the services you need.

#An editor for orca.yaml

The orca.yaml tab on a stack's page is now a proper editor: routes, links, setup commands and build targets as forms, next to the file itself, and both stay in step.

  • Pick the service and port from what the stack actually runs, and see the URL each route gives and whether it's active.
  • One click adds a route for a web service that doesn't have one yet.
  • Your comments, the dev: section and anything the forms don't cover are kept exactly as they are.
  • Checked as you type; Save waits until the file is valid.

The Projects page's orca.yaml dialog has the same editor next to the worktree settings.

#WebSockets, per project

WebSockets pass through every route as they are. For Pusher-protocol servers like Soketi, put it in the project that uses it and route /app/* on the app's own hostname: Laravel Echo and pusher-js then use the page's own host, with no shared socket server and no list of exceptions. When a stack runs Soketi, the editor offers this route, and Create orca.yaml includes it. The orca.yaml reference has the recipe.

#A landing page that's alive

The gateway's own address lists every routed service, and now shows whether each one runs and for how long: running, starting, unhealthy, sleeping or stopped. It updates whenever a container starts or stops and refreshes itself while open.

  • Give it a title and subtitle, and choose whether it shows status and the container behind each card, on the new Landing page tab of the Gateway page.
  • Each route can have a title, description, group and icon, from orca.yaml, orca.route.* labels or the Gateway page. Hide the ones nobody needs to see.
  • Worktree instances read nicely, such as "Web · feature-x".

#Fixes

  • Worktrees see optional services. Services behind a compose profile were invisible to worktree instances, because docker compose config leaves them out unless asked. Orca now reads them all and lets you pick.

v0.49.0October 22, 2026

#Set up a project with one file

Put an orca.yaml next to your compose file and commit it. Everyone who runs the project with Orca gets the same HTTPS hostnames, links to the other environments, build targets and setup commands, whether they start it from Orca or with docker compose up in a terminal.

gateway:
  - hostname: shop        # https://shop.localhost
    service: web
    port: 3000

links:
  Shop:
    - name: Storefront
      local: shop
      staging: https://staging.shop.example.com

hooks:
  after_up:
    - "web: npm run migrate"
  • Orca finds it on its own. Every compose project Orca can see gets its orca.yaml applied, and when you edit the file the change applies straight away. Routes exist while their service runs.
  • Create one in a click. The new orca.yaml tab on a stack's page writes a first version from the stack's running services, and checks it as you type. For a stack that already has one, the tab shows what Orca applied and why anything didn't apply, such as a hostname another route already uses or a service that isn't running.
  • One file for everything. Gateway routes, links, build targets, setup hooks and the dev: section for worktree instances all live together. An orca.local.yaml next to it holds settings that differ per machine. When Orca finds a repo whose orca.yaml is set up for worktrees, the Projects page offers to add it.
  • A full reference. Every key is described in the orca.yaml reference.

#Routes from container labels

A container can now ask for its own hostname. Orca adds the route when the container starts and removes it when it stops.

labels:
  orca.route: shop

Traefik labels work too, so projects that already use Host(...) rules get routed with no changes. The Gateway page tags each route with where it comes from (labels, orca.yaml, a stack or a worktree) and points you to the right place to change it.

#Hostnames work inside containers too

Every routed hostname now also resolves inside your containers, to the gateway. A backend can call https://auth.localhost the same way your browser does, which is what OIDC issuer URLs and server-to-server calls by public name need.

#Setup commands for any stack

hooks.after_up in a stack's orca.yaml runs commands after every start from Orca: migrations, creating buckets, registering search attributes. If one fails, the stack page shows its output and the rest still run.

#Fixes

  • A brand-new install works on the first start. On some first starts, Orca's window opened before its background service had created its access key, and Orca kept going without it: every page failed with "401 Unauthorized" or stayed empty until Orca was restarted. Orca now picks up the key as soon as it exists.
  • Errors say what went wrong. A failed request used to leave pages loading forever, or report "error decoding response body". Now the actual problem is shown, and System Health offers to try again.
  • Hostnames from templates work. A template route like webmail was registered as just webmail, which no browser asks for. It now becomes webmail.localhost (or your own domain).

v0.48.1October 21, 2026

#Helm only talks to Orca's cluster

Orca's Helm features ran Helm against your kubeconfig's current context instead of Orca's own orca context, which kubectl already used. If your current context pointed at another cluster, for example a remote or production one:

  • the Helm tab on the Kubernetes page listed that cluster's releases
  • installing a chart from Orca would have installed it there
  • uninstalling a release from Orca would have removed it there

Every Helm command now targets Orca's cluster only. When Orca's cluster isn't running, the Helm tab shows no releases right away instead of waiting about 8 seconds.

Please update if you use Orca's Kubernetes features and switch kubectl contexts.

#Faster

  • Volumes page: volume sizes reuse Orca's cached disk-usage scan instead of making Docker measure everything again (several CPU seconds) on every visit, and the list shows without waiting for the sizes. Refresh measures again.
  • System health checks use far less CPU, and free disk space now matches df.
  • Startup: Orca shows its window sooner. It notices the daemon is ready faster and skips a redundant environment check when Docker is already connected.
  • Projects page: with no projects yet, it no longer searches your Compose folders for suggestions every 5 seconds.

v0.48.0October 21, 2026

#Orca barely touches Docker while you're not using it

Orca's windows each fetched their own copy of the container and image lists every few seconds, even while the window was hidden. On a Mac with the containerd image store, listing 70 images costs Docker over a CPU second, and the sidebar did it every 5 seconds just to show a count.

With the dashboard open, Docker in the VM used about 150% of a core on v0.47.3. On v0.48.0 it uses about 5%, about the same as with no dashboard open at all.

  • Lists are fetched once and shared by the sidebar, dashboard and pages, and refresh the moment a container or image changes instead of on a timer.
  • Nothing polls while the window is hidden. On macOS, closing the window keeps Orca in the menu bar; it now goes quiet there.
  • Container stats come in one request for all running containers instead of one per container.
  • Kubernetes and health checks no longer start processes on every refresh (kubectl, sysctl, vm_stat, df; PowerShell on Windows).
  • Faster to open and smoother to use: pages load when you first visit them, tables update only the rows that changed, and the always-on blur effects behind the sidebar, titlebar and cards are gone.
  • Following logs is cheap: log lines arrive in batches and only the lines on screen are drawn. Following a chatty container used to keep the window's main thread busy almost all the time; now it's about 5%.

#Fixes

  • Container exit and out-of-memory notifications work. Docker's events never reached Orca, so these toasts never appeared.
  • Container CPU % shows current usage. It used to show the average since the Docker VM started. Memory now matches docker stats (page cache excluded).
  • Orca no longer opens a new Docker event stream on every launch. Each one stayed open until the daemon restarted.

v0.47.3October 20, 2026

#Docker stays quiet while Orca is idle

Orca's health check asked Docker for its disk usage every few seconds, and the titlebar, status bar and dashboard each ran their own copy of that check. Working out disk usage means Docker walks every image, container, volume and build cache entry, so an idle Orca kept Docker noticeably busy.

  • Far less work for Docker: disk usage is now read at most every 10 minutes, and the whole window shares one health check. On a Mac with 39 running containers, Docker's CPU use with the dashboard open dropped from about 40% to 18% of a core, and on other pages from about 14% to 4%.
  • Figures still update when they should: deleting or pruning images, containers or volumes, stopping a stack, and running cleanup all refresh the numbers.
  • Health checks never wait for the disk scan, so the Docker status in the titlebar stays responsive even when Docker is slow to answer.

Thanks to @diem2001 for finding this, measuring it and fixing it (#5).

#Installing Orca on a remote server

  • The install command works again. curl -fsSL https://orca-desktop.com/install-daemon.sh | sudo sh failed: the script wasn't published at that address, and on Debian and Ubuntu it stopped with Illegal option -o pipefail. Both are fixed, and it works with sudo bash too. Thanks to @erdincka for reporting it (#4).
  • The uninstall script removes Orca properly. It now uninstalls the orca-daemon package, including the orca command-line tool, and removes Orca's package repository. Before, it deleted the files but left the package registered as installed.

Both scripts are served from orca-desktop.com, so these fixes already apply to new installs.

v0.47.2October 16, 2026

#Docker no longer runs out of memory

Docker Engine versions before 29.9.1 leak a little memory every time something asks for their version, and Orca asked a lot. Over a couple of weeks the Docker VM ran out of memory and Docker was killed.

  • Orca asks far less often: the engine version is now fetched about once an hour, and health checks use a lightweight ping instead. That stops the growth even on older engines.
  • One-click Docker Engine update: if your Docker VM runs an affected version, you'll see a warning in the status bar. Click it and press Update on System Health. Orca updates Docker inside the VM, restarts it and starts your running containers again. Containers, images and volumes are kept.

Thanks to Dominic for tracking this down.

#Fixes

  • The app now restarts its daemon if it stops unexpectedly. Before, a crashed daemon left Orca showing RUNNING while nothing worked, until you relaunched. Now you see a "reconnecting" banner, the daemon comes back within a few seconds, and after repeated crashes Orca shows the connection screen instead of retrying forever.

v0.47.0October 14, 2026

#Worktree instances

Every git worktree of a compose project can now run as its own instance, with its own URLs, ports and compose project. Databases and other infrastructure run once in a shared stack. Your compose files are never modified.

  • Projects page in the app, a Dashboard card, and running instances in the tray menu
  • CLI: orca up, down, status, logs, env, run and projects, from inside any worktree
  • MCP: instance_* tools for coding agents
  • Per-instance data: shared (default), own database or own server, with reset
  • Idle stop, with wake on the next request
  • Host dev servers: orca run --serve web -- npm run dev routes the service's URL to a process on your machine

#Security

  • The gateway no longer serves its certificates folder. Before this release, the TLS private keys could be fetched from every routed hostname. Update if you use the gateway.

#Other changes

  • The gateway access log is now a rotated file (ca/certs/access.log) instead of container output
  • macOS: docker compose now works when Orca is opened from Finder or the Dock
  • macOS: the gateway can now reach dev servers running on the Mac
